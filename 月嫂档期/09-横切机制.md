# 09 · 横切机制：贯穿所有环节的四个杠杆 + 一个地基

> **环节定位**：01–08 是按生命周期拆的纵向环节；本文件是横切所有环节的通用机制——每条机制都服务于「准」或「及时」，且在多个环节复用。
> **总览**：[00-总览.md](00-总览.md)

---

## 杠杆一：信息源分级——冲突时听离事实最近的

| 优先级   | 信息源                | 为什么             |
| ----- | ------------------ | --------------- |
| 1（最硬） | 打卡（扫码 + 客户确认；定位校验暂缓） | 在场证据，伪造成本较高 |
| 2     | 客户确认               | 服务现场的一手信息       |
| 3     | 月嫂申报               | 本人最知道自己，但有粉饰动机  |
| 4     | 老师代录               | 二手转述，留「代更新」标记区分 |
| 5     | 销售录入               | 离事实最远，仅作线索不作事实  |

- 两源冲突时**高优先级源为准**，低优先级源自动降级为「待核实」；
- 每条档期变更必须记录信息源（落 `maternityNannyAuditLog`），无源变更视为异常数据。

## 杠杆二：诚实激励账——档期不准的本质是「说真话的成本 > 收益」

机制设计 = 重新定价。逐角色算账：

| 角色   | 不诚实的收益          | 对策（让诚实更划算）                            |
| ---- | --------------- | ------------------------------------- |
| 月嫂   | 不报下户 = 可以休息不被推单 | 释放档期 = 优先进入推送视野、连档奖励；报假 = 可信度分掉、销售端降权 |
| 销售   | 口头锁档 = 囤人防抢     | 锁档 48h 自动释放让囤人无收益；撞单透明化让私藏无处可藏        |
| 月嫂老师 | 代维护无回报，不维护无成本   | 担保记录留痕（确认后反悔「记小本本」）；核实列表工作量可见、进考核     |
| 客户   | 不说生产 = 无感       | 告知激励（服务券/小礼品）+ 关怀触点顺带确认               |
| 客服   | 多一事不如少一事        | 抽检核实结果进个人工作量统计                        |

**判断标准：任何一条新机制，先问「它让谁说真话更划算了吗」，答不上来的不做。**

## 杠杆三：不新增维护动作——嵌进已有动作

凡是要求人多做一个动作的机制都会衰减。维护点全部挂到既有动作上：

| 维护内容 | 挂到哪个既有动作 |
|---|---|
| 上户/下户状态 | 打卡（本来就要打） |
| 服务中存活证据 | 护理日志（本来就要写） |
| 接档意愿 | 老师上户回访挂电话前顺手登记 |
| 预产期确认 | 客户关怀/产检提醒顺带一句 |
| 档期删除 | 退款流程必经节点 |
| 意愿更新 | 推送确认卡片一键操作（不填表） |

配套原则：**每个功能都要回答「替代了哪通电话」**，答不上来的不做——防止膨胀成又一个人肉维护的表格系统。

## 杠杆四：通道分级兜底——别什么事都靠打电话

| 优先级 | 通道            | 适用场景                                |
| --- | ------------- | ----------------------------------- |
| 1   | 小程序订阅消息（定时投递） | 常规推送、确认卡片                           |
| 2   | 短信            | 12h 未响应兜底（只写「有一条档期邀约待确认」，不含薪资/客户姓名） |
| 3   | 企业微信          | 销售↔月嫂想聊聊、内部协同                       |
| 4   | AI 外呼         | 批量意向采集（费用与接通率待评估，暂作补充）              |
| 5   | 人工电话          | 老师核实列表、紧急情况挑时机直接打                   |

- 按事项紧急度选通道：锁档确认走 1–2，意愿失效走 1→5 逐级，紧急换人直接 5；
- **隐私红线**：上户月嫂手机常在客户眼皮底下，任何通道文案不出现薪资数字、客户姓名。

## 杠杆五（地基）：写入口径收口、读入口径放开

- 6 个写入口（档案、订单详情、排期表、请假审核 ×2、上下户审批）从「写入入口」降级为「**申请入口**」，实际变更统一走**档期状态机服务**，按 Sheet 20 流转表校验合法性；
- 档案端「随意改状态」关掉，只留白名单（培训中→空闲、X→长期锁档、X→离职、离职→空闲：仅超管直调或老师发起+本人确认 2026-08-27）；**老师发起的白名单调整须经月嫂本人在小程序确认后生效**（默认 48h 无确认自动作废）；**极端情况（联系不上本人）由运营负责人手动直调**，原因必填、留痕从严（2026-08-26 确认）；
- **纠错旁路 ≠ 手工补录**（2026-08-26）：录错的档期段（日期错/绑错订单/误操作）走「纠错申请 → 运营主管审批 → 状态机执行」——申请写明原始错误与正确值，执行仍过状态机校验，操作类型记「纠错」落流水；同一操作人高频纠错进运营复核（纠错率是入口质量指标）；
- 每次变更落 `maternityNannyAuditLog`：谁改的、从什么改成什么、为什么、信息源是什么；
- **读取不设限**：销售、客服、老师、运营各端按角色看全量数据——透明是协同的前提，管制只针对写。

> 这条是整个体系的地基（落地优先级第 3 位）：先管住写入（收口），再让写入变快（打卡），最后把线下的嘴也管进系统（软锁）。
