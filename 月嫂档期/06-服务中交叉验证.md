# 06 · 服务中交叉验证：活体证据 + 接档预登记

> **环节定位**：服务中的档期一般没人动它——正好用**低成本的「活体证据」持续校验**，同时把下一单的档期问题**前置到服务中解决**（接档预登记），而不是等下户才开始。
> **SLA**：交叉验证每日跑批；预登记在服务第 15 天左右自动触发。
> **总览**：[00-总览.md](00-总览.md)

---

## 一、这个环节档期会怎么不准

| # | 失真场景 | 后果 |
|---|---|---|
| 1 | 人在户上但系统没记录（换人漏录的残留） | 系统显示空闲，推送空发，水位虚高 |
| 2 | 人已下户系统还显示上户中 | 可售池漏掉一个真实供给 |
| 3 | 服务中请假口头跟老师说，没进系统 | 档期显示可售实际不可售 |
| 4 | 下户后接档意愿没人问，下户了才开始找单 | 等单天数拉长，连档断裂，供给浪费 |

## 二、要做的事

### A. 活体证据交叉验证

- **护理日志是最便宜的活体探针**：她每天在写护理日志 = 人大概率在户上；**日志中断 > 2 天但档期显示上户中** → 进异常清单；
- 多源互证：日报、保险生效状态、客户回访记录——任何两源矛盾都进对账清单（见 [08-事后对账与抽检.md](08-事后对账与抽检.md)）；
- 这条链路的成本几乎为零：数据本来就在产生，只是拿来做交叉。

### B. 接档预登记（更根本的解法）

- 26 天单服务到**第 15 天左右**，系统自动给上户月嫂发「接档登记」卡片：

> 你的单子预计 X 月 X 日下户，下户后怎么安排？
> [ 休 3-5 天就接 ] [ 休一周以上 ] [ 直接连档 ]　想接几月上户的：____

- 登记后，后续推送从「询问」降级为「确认」（「你登记过想连档，10.22 这单确认接吗？」）——确认成本远低于询问；
- **未登记的自动进月嫂老师核实列表**：触达责任从销售转移到老师；老师上户回访挂电话前顺手登记（嵌进既有动作，不新增维护动作）。

### C. 上户中触达适配（不追求实时，用时机绕开）

- 上户月嫂白天带娃做饭、手机看得少，「4 小时确认」不成立：
  - **定时投递**：按手机窗口规律（12:30–14:30 / 20:00–21:30）送达，时限从送达起算；
  - 确认时限默认 **12 小时**；一轮未响应，晚 20:00 自动再推一次；
- **隐私红线**：上户月嫂的手机常在客户眼皮底下，推送文案**不出现薪资数字、客户姓名**，细节点进小程序才可见。

### D. 服务中请假

- 上户期间请假走专门审核入口（月嫂小程序发起 → 后台审核 → 改档期表），**请假叠加层优先级最高**，覆盖期间不可售（Sheet 20 口径）；
- 口头请假没录系统的，靠 A 的交叉验证（日志中断/客户回访发现）兜底捞回。

## 三、责任角色

| 角色   | 责任                         |
| ---- | -------------------------- |
| 系统   | 交叉验证跑批、预登记卡片触发、定时投递、异常清单生成 |
| 月嫂   | 护理日志如实填写、预登记一键操作           |
| 月嫂老师 | 上户回访时顺手确认接档意愿、核实列表兜底       |
| 客服   | 回访记录作为交叉源之一                |

## 四、指标

- **预登记率**（服务中月嫂完成接档登记的比例）；
- 上户中推送响应率（定时投递后）；
- 交叉验证异常条数 / 确认属实率（衡量探针灵敏度）；
- **连档率**（下户后 7 天内接上档的比例）——预登记的最终效果指标。
