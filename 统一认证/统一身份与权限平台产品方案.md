## 术语与概念（建议先读）

> 本文涉及的专业名称在此统一口径。每条附一个例子，确保所有读者理解一致。

### 认证层

| 术语 | 含义 | 例子 |
|---|---|---|
| account（账号） | 登录身份，只存认证信息（登录标识、凭证、状态），不存业务数据 | 张翠花的手机号 138****2046 在平台有一条 account |
| 主体（party） | 业务身份，业务数据的挂载点；一个 account 可绑多个主体 | 张翠花既是客户又是月嫂：她的 account 下挂 customer 和 worker 两个主体 |
| 五类主体 | customer（家庭客户）/ worker（月嫂护理）/ staff（内部员工）/ promoter（推广者）/ agency_user（机构管理员，二期） | 应聘者留资即成为 promoter；机构管理员二期才有 |
| 绑定（bind） | account 与主体的关联关系，1:N 双向 | 微信登录的 account 绑 customer 主体后，才能在客户端下单 |
| channel（端） | 端的标识，登录时区分来源 | 客户端小程序=`client_mini`，业务管理后台=`admin_web` |
| token | 登录成功后签发的"门禁卡"，卡面：你是谁 + 从哪个端 + 以什么主体 + 数据范围 | 刘倩登录 ERP 拿到的 token：account=刘倩、channel=admin_web、主体=staff、数据范围=本部门及下级 |
| 网关三校验 | 每个请求过三关：token 有效 + 主体状态正常 + 主体类型允许进入该端 | 被拉黑的 worker 登录月嫂端，在第二关被拦下 |
| unionid / openid | 微信生态标识：openid 是一个微信在一个 AppID 下的标识，unionid 在同一开放平台账号下不变 | 同一微信在客户端和月嫂端小程序 openid 不同、unionid 相同 → 识别为同一个人 |

### 开户与生命周期

| 术语 | 含义 | 例子 |
|---|---|---|
| 无感知注册 | 新手机号/新微信首次登录即自动开户，首登弹用户协议 | 新客户在客户端输入手机号+验证码，登进去时账号已建好 |
| 邀请制开户 | 员工/机构不能自注册，管理侧建档后邮件邀请激活 | HR 给新员工林涛建档，他收到邮件链接设密码后才算开户完成 |
| 存量批量开户 | 既有系统（ERP）在营员工的批量建档：导花名册 → 批量邀请 → 激活即完成绑定 | ERP 300 名员工一次性迁入统一认证 |
| 首登准入联动 | worker 首次登录月嫂端时，手机号命中已建档记录则自动绑定 | 张翠花被公司建档后，第一次登录月嫂端就关联上自己的档案 |
| guide_status | 登录响应里的引导状态字段：认证中心只给状态码，引导页面由各端自己做 | 未建档的月嫂登录时返回 `WORKER_ONBOARDING`，月嫂端跳"去招聘端留资"引导页 |
| 两级禁用 | 按主体禁用（封身份）与按账号禁用（封号）分开 | 拉黑张翠花的月嫂身份（她不能接单），但她还能用客户身份下单 |
| 冷静期 | 注销申请后保留 7~15 天可撤销的缓冲期 | 客户申请注销后第 3 天反悔，登录点"撤销注销"即恢复 |
| 二次放号 | 运营商回收手机号再放出，新号主登录时发现旧号主的账号 | 李强新办的手机号登录客户端，看到别人的订单 → 走"这不是我的账号"申诉 |
| 墓碑记录（二期） | 被合并账号的只读存档，用于审计追溯 | 两个账号合并后，原账号不可登录但可查到"它并入了谁" |

### 权限层（RBAC）

| 术语 | 含义 | 例子 |
|---|---|---|
| RBAC | 基于角色的访问控制：权限不直接给人，而是"角色打包权限点、人挂角色" | 刘倩挂「销售主管」角色，而不是逐个给她配按钮 |
| 权限点 | 系统里最小的一个受控动作，编码带系统前缀 | `scrm:lead:assign` = SCRM 线索管理的"分配"操作 |
| 角色 | 权限点的打包组合，可跨系统 | 「客服」= 认证中心账号查询 + 申诉审核 |
| 权限树按菜单归类 | 权限树的层级就是业务系统的菜单结构（模块 ▸ 页面 ▸ 页签） | 配 ERP 权限时看到的树和 ERP 侧边栏长得一样 |
| 页签（⧨） | 页面内的页签是独立权限资源，有独立动作与数据范围，默认跟随父页 | 「审核中心」页面下，销售主管只见"订单变更"页签，月嫂主管只见"在户请假"页签 |
| 数据范围（data_scope） | 角色能看多大规模的数据，全公司统一六档：本人/本人及下属/本部门/本部门及下级/全机构/自定义部门 | 产康店长梁欣是"本部门"= 只见北滘店数据 |
| 基准档与收窄 | 角色定基准档（上限），具体页面只能收窄不能放宽 | 销售主管基准"本部门及下级"，但工资单页收窄到"本部门" |
| 自定义部门 | 不按部门树层级、横向圈选若干部门节点的范围档位 | 给某运营圈"佛山分部 + 中山分部"两个不相邻节点 |
| 高风险动作 | 资金/不可逆类操作，配置界面标 ⚠，执行要求二次验证与审计 | 发放工资、退款、作废合同 |
| 互斥规则 | 同一角色在同一页面不得同时持有互斥动作（不可自审） | 工资账单页的「生成」和「发放」不能都给一个人 |
| 集中管理、分布执行 | 角色与授权只在统一管理后台维护；各业务系统按 token 本地校验 | 管理员在后台改一次角色，ERP/SCRM 各自本地生效，不用逐个系统配 |

### 系统接入与治理

| 术语 | 含义 | 例子 |
|---|---|---|
| manifest | 系统接入时注册的清单：菜单结构（sitemap）+ 权限点集合 | SCRM 构建时自动生成 manifest 同步到权限模块 |
| 防重（注册查重） | 注册侧的前置闸：unionid/手机号查重，重复账号在产生前拦截 | 同一微信登录月嫂端时查到已有 account，直接登录而不是新建 |
| 身份归并（二期） | 发现两个账号是同一人后的合并治理（自动归并/引导合并/人工合并/墓碑） | 一期不做，重复 case 走"客服提单 → 开发脚本" |
| 企微 memberid | 企业微信成员 ID，staff 与企微的绑定键 | 员工企微扫码登录后台，靠 memberid 匹配到 staff 档案 |
| 离职三连 | 员工离职的联动处置：禁账号（必执行）+ 企微处置二选一（禁用并继承客户 / 保留企微号） | 销售离职：账号全端失效；企微号公司留下给继任者用则选"保留" |
| 审计日志 | 只追加、不可改的操作留痕 | 谁几点从哪个端禁用了哪个账号，出问题全靠它倒查 |
| 二次验证 | 高危操作需操作人再验一次（短信验证码/密码） | 管理员禁用账号前要输一遍自己手机收到的验证码 |
| SSO（二期） | 单点登录：内部多后台一次登录通行 | 登录一次，ERP 和统一管理后台都能进 |
| MFA（二期） | 多因素认证：密码之外的第二因子 | 管理端敏感操作触发 OTP 动态码 |

## 1. 背景与问题

公司当前规划 8 个端：**客户端小程序**（家庭客户）、**客户端 APP**（家庭客户）、**月嫂端小程序**（月嫂/护理人员）、**月嫂端 APP**（月嫂/护理人员）、**月嫂招聘小程序**（应聘者留资 + 推广者）、**内部员工端小程序**（员工）、**业务管理后台**（员工）、**SCRM 系统**（员工，自研待建），覆盖家庭客户、护理人员、内部员工、推广者四类主体（外部机构为二期规划）。如果各端各自建设账号体系，将产生以下问题：

| 问题 | 具体表现 |
|---|---|
| 账号割裂 | 同一人在不同端是多个"账号"，数据无法打通（如月嫂同时是客户时无法识别） |
| 重复建设 | 每个端重复实现登录、凭证、权限校验，开发与安全成本高 |
| 安全失控 | 密码策略、锁定策略、敏感操作管控各端不一，无法统一治理 |
| 离职/黑名单难执行 | 员工离职、人员拉黑后，各端账号需要逐个处理，存在残留权限风险 |
| 无统一审计 | 出问题无法回答"谁在什么时间从哪个端做了什么" |

---

## 2. 目标与价值

1. **统一认证**：所有端共用一个认证中心，一处签发、处处校验。
2. **身份与主体分离**：认证身份（account）与业务主体（customer / worker / staff / promoter / agency_user）解耦，一人可有多重身份。
3. **统一安全治理**：登录策略、锁定策略、敏感操作验证、审计集中管理。
4. **降低接入成本**：新业务端接入登录降为配置级工作，不再重复开发。

## 3. 产品定位与边界

### 3.1 职责切分

| 问题 | 谁回答 |
|---|---|
| 你是谁？能不能登录？ | 认证中心（登录认证、token） |
| 账号正不正常？有几个身份？ | 认证中心（账号状态、绑定关系） |
| 进来后能看什么、点什么？ | 统一管理后台 · 权限模块（RBAC） |
| 员工是谁、在哪个部门？ | 统一管理后台 · 组织与员工（员工主数据） |
| 档案、订单、钱包在哪？ | 各业务系统 |
| 出了问题谁做的、什么时候？ | 认证中心（审计日志） |
| 客户关系与跟进归谁？ | SCRM（自研业务系统：登录走统一认证、角色权限走统一 RBAC；客户资源分配属业务数据，归 SCRM 自己） |
| 页面谁做？ | 各端（认证中心只下发状态码与文案） |

### 3.2 "不做什么"清单（防范围蔓延）

- 不存储业务字段（等级、积分、余额、订单）——认证中心只存身份与凭证。
- 不实现业务侧的功能权限配置界面——只提供身份数据接口，供统一管理后台的权限模块（RBAC）使用。

## 4. 整体方案

### 4.1 核心模型：账号与主体分离

**平台组成**——本平台由三部分协同构成，各业务系统经标准机制接入：

```text
┌─ 统一身份与权限平台 ─────────────────────────────────────────┐
│  统一认证中心        登录认证 / 账号状态 / 绑定关系 / 审计     │
│  统一管理后台        组织与员工 · 权限模块(RBAC) · 账号管理    │
│                     · 全局配置 · 审计查询                     │
│  API 网关            token 校验 / 主体状态 / 端准入 / 数据隔离 │
└──────────────────────────────────────────────────────────────┘
        ▲ 统一登录 API                    ▲ 权限点注册 + 本地校验
        │                                │
   8 个端（小程序/APP/后台/SCRM）  各业务系统（ERP / SCRM / …）
```

```text
        客户端             月嫂端            招聘端       员工端      业务管理后台   SCRM
     小程序 + APP       小程序 + APP        小程序       小程序
         │                 │                 │            │              │          │
         └─────────────────┴────────┬────────┴────────────┴──────────────┴──────────┘
                              ▼
                 ┌─────────────────────────┐
                 │   统一认证中心（account）  │  解决"你是谁、能否登录"
                 │ openid/手机号/用户名+凭证 │
                 └────────────┬────────────┘
                              │ 1:N 绑定
        ┌──────────────┬──────┴───────┬──────────────┬─────────────┐
        ▼              ▼              ▼              ▼             ▼
   customer        worker         staff        promoter      agency_user      解决"你能做什么"
   家庭客户        护理人员        内部员工      推广者/介绍人  机构管理员（二期）

   注：月嫂招聘小程序的用户统一建模为 promoter 主体（首次登录无感知创建）——
   应聘与推广是一个人的两种行为：自己应聘生成"自荐"线索，推荐他人生成"推荐"线索，
   均挂 promoter 主体；佣金结算等数据同挂。
```

**原则**：

- `account` 只存认证信息（登录标识、凭证、状态），不存业务数据。
- 五类主体各自建模，业务数据全部挂主体，换绑登录方式不丢数据。
- 一个 `account` 可绑定多个主体（一人多角色）；一个主体可被多个 `account` 绑定（如夫妻共用家庭账号）。
- 认证中心签发 token 时携带「端 + 主体类型 + 主体ID + 数据范围」；数据范围仅 staff 主体有值（六档），其余主体恒为空——C 端数据隔离由业务系统按 party_id 属主校验，不经 data_scope。网关按 token 校验准入与数据隔离。
- **家庭多账号可见性**：同一主体被多个 account 绑定时，默认共享该主体全部业务数据（家庭共享语义，适用于夫妻共用场景）；一期不支持主体内成员级数据隔离——如需"孩子账号不可见订单"类诉求，另建主体（家庭成员档案），不走多 account 绑定。

**账号状态机**——`status` 枚举与流转（一期）：`未激活 / 正常 / 锁定中 / 已禁用 / 冷静期 / 已注销`（墓碑属二期）：

```text
[*] ─ 邀请制开户（员工/存量批量）→ 未激活 ─ 激活设密（72h 内）→ 正常
[*] ─ 无感知注册（C 端验证通过）→ 正常
未激活 ─ 激活逾期回收（30 天）→ [*]
正常 ─ 连续失败达阈值（默认 5 次）→ 锁定中 ─ 到时自动解除（默认 30 分钟）→ 正常
正常 ─ 管理侧禁用（原因必填+二次验证）→ 已禁用 ─ 管理侧启用（二次验证）→ 正常
正常 ─ 注销申请通过前置校验 → 冷静期 ─ 期内登录并确认撤销 → 正常
冷静期 ─ 到期执行（凭证失效+匿名化）→ 已注销（终态，业务记录按法规留存）
```

**员工与账号的三层关系**（员工场景的具体化）：

```text
员工（人，HR 主数据）         staff 主体（权限层身份）        account（认证层钥匙）
姓名/部门/岗位/在职状态  1:1   role_ids / data_scope    N:1  手机号/微信/密码/状态
在统一管理后台（组织与员工）    （员工档案自带的权限属性）        在统一认证中心
```

- 员工回答"这个人是谁、在哪个部门、在不在职"（管"人"）；账号回答"他怎么登录、能不能登录"（管"钥匙"）；staff 主体是两者之间的桥。
- 三者不必然成对：建档未激活 = 有员工没账号；客户/月嫂/应聘者/推广者 = 有账号不是员工；一人多角色（如张翠花兼 staff 与 customer）时员工这层关系只覆盖 staff 主体。
- 生命周期联动：入职 = 建档 → 邀请 → 激活设密（绑定 account + staff 主体）；调岗 = 改部门/角色 → role_ids/data_scope 随下次 token 生效；离职 = 员工状态改"离职" + 禁 account（≤5s 全端失效）+ 企微处置二选一（禁用并继承客户 / 保留企微号继续使用）——**人走、档留、钥匙收**。
- 员工场景实际为 1:1，但架构不写死（绑定关系 N:M），为"代查账号/值班账号"类需求留余地。
- **员工多部门**：员工有且仅有一个主部门（汇报线与离职归属），可有多个兼任部门；数据范围「本部门 / 本部门及下级」按 **主部门 ∪ 兼任部门** 计算，"及下级"对兼任部门同样下钻（如分部主管兼任另一分部，该分部及其下辖门店数据均可见）。

### 4.2 关键设计决策

| 决策 | 内容 | 理由 |
|---|---|---|
| 多登录方式可插拔 | 微信 code、手机号验证码、账号密码、企微扫码均抽象为"认证源" | 新增登录方式不改核心代码 |
| 按端准入 | 主体类型 + 主体状态决定能否进入某端（如黑名单 worker 登录即拦截） | 禁用动作一处生效，处处拦截 |
| 两级禁用 | 按主体禁用（拉黑月嫂身份）与按账户禁用（封号）分开 | 避免误伤用户的其他身份 |
| 合并留痕 | 账号合并不可逆，保留原账号"墓碑记录" | 可追溯、可审计 |
| 数据范围正式建模 | staff 建模即含 `data_scope`，六档（本人/本人及下属/本部门/本部门及下级/全机构/自定义部门），token 签发即携带；角色设基准档、页面级可收窄 | 覆盖"本部门及下级门店"等真实层级需求，模型一次到位 |
| 业务页面不落地认证中心 | 登录响应以 `guide_status` 引导状态字段表达准入等场景，页面由各业务端承接 | 保持认证中心"不感知业务"的边界 |
| 招聘端主体模型：promoter | 月嫂招聘小程序开放注册；用户统一建模为第五类主体 `promoter`（首次登录无感知创建并绑定）：自荐留资与推荐他人都是线索（挂 promoter 主体），推广档案、佣金结算同挂；应聘者转化路径：线索 → 邀约面试 → 建档 worker → 首登手机号匹配绑定（复用同一 account）；招聘端准入 = promoter | 应聘与推广是一个人的两种行为，不应拆成两类人；主体化后佣金结算（涉资金/实名）、注销前置校验（未结算佣金阻断）、换绑双验证等标准流程自动适用，网关准入模型全端统一、无"无主体开放"例外 |
| 管理控制台归属 | 挂入规划中的统一管理后台（注意：**不是**业务管理后台，后者仅是 staff 的业务端之一） | 复用统一登录与菜单体系，长期使用成本最低 |
| 权限能力归属 | 不单独建权限中心；RBAC 作为统一管理后台的内置模块（角色→权限点映射、菜单配置）；认证中心只在 token 携带 role_ids/data_scope（身份标签），规则配置归权限模块 | 权限规则变化频繁而认证中心需保持稳定；统一管理后台本就是角色与权限点的配置入口；未来业务变多可剥离为独立权限中心，认证中心侧零改动 |
| SCRM 权限边界 | SCRM 为自研系统，按"集中管理、分布执行"接入：登录走统一认证（企微扫码 + memberid 映射 staff）；角色与权限点注册到统一管理后台权限模块，本地执行校验；客户资源分配（谁能跟进哪些客户）属业务数据归属，仍归 SCRM 自身规则；离职三连：禁账号 + 禁企微成员 + 触发客户继承 | 自研系统无"产品内置角色改不动"的限制，纳入统一治理消除离职残留与客户跟进的权限死角；客户资源分配是业务数据而非权限点，不进 RBAC |

### 4.3 权限体系（RBAC：集中管理、分布执行）

通用生命周期（新系统接入，以 SCRM 为例）——

1. **注册**（开发侧）：SCRM 将权限点清单同步到统一管理后台权限模块（`scrm:lead:view` 线索查看、`scrm:lead:assign` 分配等，接口同步或配置文件导入，非管理员手工录入）；
2. **建角色**（管理员）：权限矩阵按「系统 ▸ 模块 ▸ 页面 ▸ 动作」勾选，或复制已有角色后微调；
3. **授权**（管理员）：在员工详情页给员工挂角色；
4. **运行时**：token 携带 role_ids，业务系统按本地缓存的"角色→权限点"映射校验（不每次请求回调权限模块）；
5. **变更**：系统改版新增功能 → 增量注册权限点 → 角色按需补勾，只改统一管理后台一处。

存量系统接入（以 ERP 为例）——

1. **盘点**：输出「页面 × 动作 × 数据范围」矩阵（ERP 实践：全量盘点后标注遗留通配/缺失）；
2. **业务确认**：逐页确认动作全集与责任字段（盘点报告为待确认建议稿，业务签字为准）；
3. **生成 manifest 注册**：以确认结果为准注册权限点，**不导入旧通配权限**（如旧 `manage`）；
4. 接入后按通用生命周期维护（增量注册、废弃权限点提示引用角色）。

**manifest 字段约定**（开发对接契约）：

| 字段 | 说明 |
|---|---|
| `system` | 系统编码（权限点命名空间前缀，如 `scrm`） |
| `sitemap` | 菜单树：模块 ▸ 页面 ▸ 页签，各节点含 `menu_key`（权限树按此归类，与菜单同源） |
| `permissions[]` | 权限点：`code`（系统前缀）、`name`、`type`（page/op）、`parent`、`actions[]`、`status`（active/deprecated） |
| `version` / `generated_at` | manifest 版本与生成时间 |

废弃规则：`deprecated` 权限点至少保留一个版本周期；引用它的角色在权限点清单（P3）高亮提示，清理后方可下线。

关键规则——

- **权限树按菜单结构归类**：权限树层级 = 业务系统的菜单结构（一级模块=菜单分组 ▸ 侧边栏页面 ▸ ⧨页内页签），权限点与菜单一处维护、同源注册——菜单改版时权限树自动跟随；管理员的配置心智是"这个角色能不能看到这个菜单"，而非对着抽象资源列表。
- 权限点以系统为命名空间隔离（`scrm:` / `order:` / `account:`），注册边界在系统侧；角色是跨系统的组合器（如"客服主管"= 账号查询 + 订单查看 + SCRM 线索）。
- **数据范围六档**（本人/本人及下属/本部门/本部门及下级/全机构/自定义部门圈选）：角色设**基准档**，页面级可**收窄、禁止放宽**（如销售主管基准"本部门及下级"，工资单页可收窄到"本部门"）；「自定义部门」仅在基准档 ≥ 本部门及下级时开放圈选；数据过滤由框架统一执行，不靠逐页面开发。
- **高风险动作**（删除/作废/发放/付款/退款等）：配置界面标记 ⚠，执行要求 MFA、幂等与审计留痕。
- **互斥规则**：同一角色在同一页面不得同时持有互斥动作（提交+审核、登记+审核、生成+发放等，不可自审），配置时实时提醒。
- **发布机制**：权限配置按草稿/发布两阶段，发布时输出变更 diff（新增/移除动作、范围变化）供确认，发布后对该角色全部成员即时生效，全量留审计。

### 4.4 新端与新系统接入流程

**A. 新小程序（端）接入**——接的是登录认证，目标是"配置级"：

1. **微信侧**：新小程序绑定到同一微信开放平台账号（unionid 归并前提，上线检查项）；
2. **登记端**：分配 channel，配置端×主体准入映射（统一管理后台「端与准入管理」，免发版生效）；
3. **认证源**：配置该端启用的登录方式（「认证源配置」）；
4. **端开发**：SDK 调统一登录 API，处理 `guide_status` 引导态与禁用提示（文案平台下发）；
5. **联调验收**：登录成功/失败码、准入拦截、禁用 ≤5s 生效。

**B. 新业务系统接入**——A 线（登录）+ 权限接入：

1. 系统登记（「系统接入管理」P6：名称/编码/负责人，编码即权限点命名空间）；
2. manifest 导入：新系统 = 代码注解扫描（菜单 sitemap + 权限点随构建同步）；存量系统 = 盘点「页面×动作×数据范围」→ 业务确认 → 导入（不导入旧通配权限）；
3. 发布生效，权限点进入清单；
4. 进入日常循环：建角色（勾选或复制）→ 授权（员工详情挂角色）→ 运行时本地校验 → 系统改版增量注册、角色按需补勾。

> 接入成本 = SDK 对接 + 权限点清单梳理（存量系统最贵的是盘点确认），其余均为配置——这是"新端接入 ≤ 2 天"目标（二期验收）成立的逻辑。

## 5. 核心功能设计

### 5.1 登录认证

| 功能 | 分期 | 说明 |
|---|---|---|
| 统一登录 API | 【一期】 | `POST /api/auth/login`，按 channel 区分端与凭证类型 |
| 手机号验证码登录 | 【一期】 | 新号码无感知注册（首次登录即开户，配合用户协议弹窗） |
| 微信 code 登录 | 【一期】 | `jscode2session` 换 openid/unionid；多 AppID 靠 unionid 归并 |
| 账号密码登录 | 【一期】 | 内部后台员工使用，密码强度策略可配置 |
| 企微扫码登录 | 【一期】 | 内部后台，依赖 staff 与企微 memberid 映射（绑定机制见 5.2 企微绑定与通讯录同步） |
| 运营商一键登录 | 【二期】 | App 端默认登录方式，提升转化 |
| 登录方式优先级配置 | 【二期】 | 按端配置默认方式排序：一键 > 扫码 > 验证码 > 密码 |

**登录后身份选择**：账号绑定多主体时——单身份直接进入；多身份记住上次选择并支持切换。切换入口在各端"我的"页，认证中心提供主体列表接口。

**统一认证流程**：

1. 各端调用统一登录接口，携带 channel（端标识）与凭证。
2. 认证中心校验凭证，查 account。
3. 查主体绑定关系，返回该 account 在**当前端可用**的主体列表（按端×主体类型映射过滤）。
4. 签发 token：`{account_id, channel, party_type, party_id, 数据范围}`。
5. 网关对每个请求校验：token 有效 + 主体状态正常 + 主体类型允许进入该端。

### 5.2 注册与开户

| 功能 | 分期 | 说明 |
|---|---|---|
| 无感知注册 | 【一期】 | 新手机号/新微信首次登录自动开户；业务档案由业务系统后续补全 |
| 邀请制开户（员工） | 【一期】 | 员工账号不允许自注册：后台开通 → 邮件邀请 → 激活设密 |
| 邀请制开户（机构） | 【二期】 | 机构审核通过后为其管理员开通，激活后绑定 agency_user 主体 |
| 存量员工批量开户 | 【一期】 | ERP 在营员工：HR 批量建档（导入花名册）→ 批量发送邀请邮件 → 员工激活设密后自动完成 account + staff 绑定 + 企微 memberid 匹配；与日常邀请制复用同一流程，仅入口不同 |
| 首登准入联动 | 【一期】 | worker 首登手机号命中已建档记录则自动绑定，否则进入准入审核流程 |

**邀请链接的逆向分支**：链接 72 小时过期或员工误删邮件后，管理员在员工详情「重发邀请」（原链接作废，可多次重发）；超过 30 天未激活的账号标记「激活逾期」，支持一键回收。

**企微绑定与通讯录同步（staff ↔ wework_userid）**：

- **存量员工（首次接入）**：从企微通讯录拉取成员，按手机号匹配员工档案，memberid 批量回写 staff 表（一次性脚本/管理员工具）；
- **新员工（日常增量）**：员工建档（开通流程）时调企微 API 创建/查询成员，memberid 自动回写——与离职三连"禁企微成员"复用同一集成通道；
- **兜底**：手机号匹配不上时，管理员在员工详情页手工补绑（须核对手机号防绑错）。
- **同步方向为单向**：员工主数据只在统一管理后台维护，企微通讯录为下游副本（入转调离推送到企微，保证 SCRM 依赖的部门树同步）；不允许企微侧手工变更回流，防止双向漂移（可定期对账拉回）。

| 功能 | 分期 | 说明 |
|---|---|---|
| token 签发/刷新/吊销 | 【一期】 | 支持 refresh-token；吊销后全端秒级失效 |
| 多端在线策略 | 【一期】 | 可配置：允许同时在线端数、是否新登录踢旧端 |

### 5.4 身份归并（本产品最复杂的模块）

> 一期只做「防重」（注册查重），归并治理工具（自动归并/引导合并/人工合并操作台/自助认领/墓碑记录）在二期建设。依据：全新系统无存量重复账号，防重闸（unionid + 手机号查重）在注册侧已拦截主要重复来源；过渡期重复 case 走"客服提单 → 开发脚本合并"；数据模型按 1:N 预留，二期补建零返工。回补信号：月重复 case > 20 单或合并类工单明显上升时提前到 1.1。

| 功能 | 分期 | 说明 |
|---|---|---|
| 注册查重（防重） | 【一期】 | 归并在注册侧的前置闸：unionid 查重、手机号查重；微信登录后尽早绑定手机号——重复账号在产生前拦截（实现在 5.1/5.2，不属于本模块建设项） |
| 自动归并 | 【二期】 | 证据强时自动执行：同 unionid、同手机号验证码验证 |
| 引导合并 | 【二期】 | 登录时检测到疑似重复账号，向用户展示合并引导页 |
| 人工合并操作台 | 【二期】 | 客服侧界面：按手机号/openid 查账号与绑定主体、预览合并影响、执行合并（二次验证） |
| 自助认领 | 【二期】 | 用户提供证据（短信验证等）认领已有档案（主场景已由 worker 首登绑定覆盖） |
| 冲突决策规则 | 【二期】 | 两个主体均有业务数据时的处理规则。当前业务不存在此类冲突，按默认预案执行（订单归并到保留主体、worker/customer 仅归并绑定关系、冻结/黑名单禁止合并），不构成开发前置条件 |
| 墓碑记录 | 【二期】 | 被合并账号保留只读记录，支持审计追溯 |

**合并流程产品要点（二期）**：

1. 触发：登录检测 / 客服查询 / 用户自助。
2. 预览：合并前必须展示"将发生什么"（保留哪个账号、订单与档案如何归属）。
3. 确认：执行人（用户/客服）二次确认；客服操作需二次验证。
4. 执行：绑定关系迁移、原账号置为墓碑状态。
5. 留痕：操作人、时间、前后状态全部入审计日志。

### 5.5 账号生命周期与自助服务

| 功能 | 分期 | 说明 |
|---|---|---|
| 找回密码 | 【一期】 | 手机号验证重置 |
| 换绑手机号 | 【一期】 | 新旧号码双验证；不影响既有微信绑定（unionid 绑定关系不变）；旧号码停机时走申诉通道（证明材料 + 人工审核） |
| 账号禁用/启用（管理侧） | 【一期】 | 按账户与按主体两级，均留审计 |
| 绑定/解绑微信 | 【一期】 | 解绑后须保证账号仍至少有一种可用登录方式，否则阻断 |
| 微信不可用备用验证链 | 【二期】 | 手机号 + 人脸 |
| 账号注销 | 【一期】 | 前置校验（无在途订单/余额/欠款/未结算佣金）→ 冷静期（7~15 天，可撤销）→ 凭证失效 + 个人信息匿名化；业务记录按法规留存 |
| 二次放号处理 | 【一期】 | "这不是我的账号"申诉入口 + 入网证明换绑流程 |

**注销前置校验的接口归属**：认证中心定义统一校验接口（输入 party_type + party_id，返回是否阻断 + 阻断项清单），各业务系统按主体类型实现并注册校验项（订单→交易系统、余额→钱包、未结算佣金→招募系统）；校验项调用超时按"暂不通过 + 提示稍后重试"处理，避免业务系统故障堵死注销。

**注销前置校验不通过时**：明确告知用户卡在哪一项、去哪个端处理，给出直达入口。

### 5.6 管理控制台（运营与治理界面）

**管理口径：管全部 account，不分 C 端 B 端。** 认证中心的 account 表只有一种"登录的人"——客户、月嫂、员工、推广者、应聘者都在同一张表里，"是什么人"由绑定的主体决定（见 4.1）。因此账号管理只有一个入口：客服输入手机号/openid/账号 ID，查到任何人（不管是客户还是员工）的账号状态、绑定的所有主体、最近登录记录，不需要先问"你是哪类用户"。

但管理动作因开户方式不同而不同：

| | C 端账号（客户/月嫂/应聘者/推广者） | 员工账号 |
|---|---|---|
| 开户方式 | 无感知注册（自助，首登自动开户） | 邀请制开户（管理侧开通） |
| 管理侧动作 | 查询、禁用/启用、申诉审核（人工合并属二期） | 开通、调岗、离职禁用、凭证重置 + 查询、禁用 |
| 日常路径 | 用户自助为主（换绑/注销/申诉），客服只接申诉 | 管理侧全生命周期 |

另注意「账号 ≠ 业务档案」的边界：账号状态、禁用（按 account 级）归管理控制台；主体业务状态（如 worker 黑名单、客户标签）归各业务系统维护——两级禁用正对应这条边界，网关同时校验两者。

> 控制台全部界面定义见《统一管理后台功能与页面清单.md》（账号管理 M1~M4、权限管理 P1~P6、全局配置 G1~G5、审计 L1），原型见 `prototype/`。

| 功能 | 分期 | 说明 |
|---|---|---|
| 账号查询 | 【一期】 | 按手机号/openid/账号ID 查账号状态与全部绑定主体 |
| 账号禁用/启用 | 【一期】 | 两级禁用操作入口，强制填原因、留审计 |

## 6. 交付规划与里程碑

### 一期：统一登录底座 + 身份治理

- 范围：account + 主体绑定模型（含 staff 正式建模 role_ids/data_scope）；统一登录 API（含 `guide_status` 引导状态字段）；验证码/微信 code/密码/企微扫码登录；无感知注册（含 unionid/手机号注册查重防重）；邀请制开户；token 体系（签发即携带数据范围）；账号查询/禁用/凭证重置；员工账号管理；防爆破与敏感字段加密；换绑/注销/申诉；多端在线策略；敏感操作二次验证；审计记录与查询界面；认证源与安全策略配置。（身份归并治理工具缓至二期，见 5.4）
- 验收：
  - 首个业务端按统一登录规范完成接入；禁用账号全端秒级生效；
  - 重复账号率 < 1%（防重口径：unionid + 手机号注册查重全量生效）；重复 case 有"客服提单 → 开发脚本"处理通道；账号类工单自助解决率 > 60%。
- 验收指标口径：
  - **重复账号率** = 当期判重（同 unionid / 同手机号）命中的账号对数 ÷ 活跃 account 数（近 30 天有登录），按月统计；
  - **账号类工单自助解决率** =（换绑 + 注销 + 申诉）自助完成量 ÷ 账号类客服工单总量，按月统计，工单分类以客服系统为准。
- 关键依赖：认证中心需先于或同步于各业务端开发，作为所有端的登录底座；管理控制台挂入统一管理后台（「账号管理」模块），需与该后台团队对齐菜单与权限点。
- 迭代建议（共 4 个迭代 + 收尾）：
  1. 模型底座 + 登录与 token——关键路径，完成后业务端即可并行接入；
  2. 开户 + 安全审计基础 + 企微扫码登录——与第 1 迭代部分并行；
  3. 管理控制台 + 自助服务——界面工作量集中在此；
  4. 安全增强（二次验证/多端在线/策略配置）与 P1 项收尾；
  5. 收尾：压测、故障演练、法务过审、数据模型评审。

### 二期：安全增强与开放能力

- 范围：身份归并治理（自动归并、引导合并、人工合并操作台、自助认领、墓碑记录）；SSO 单点登录/登出；MFA；运营商一键登录；人脸备用验证；应用注册管理。
- 验收：新端接入 ≤ 2 天；重复账号率 < 1%；重复账号合并有不依赖开发的操作路径。

> 分期原则：一期数据模型必须兼容二期（绑定关系按 1:N 设计，禁止按一对一写死；数据范围字段为正式建模，非过渡）。

## 7. 风险与依赖

| 风险/依赖 | 影响 | 应对 |
|---|---|---|
| **认证中心与业务端的排期先后**（关键依赖） | 各端未开发，认证中心是所有端的登录底座，若底座延期则阻塞所有端 | 一期第 1 迭代优先交付"统一登录 API + token 体系 + SDK/接入文档"，让业务端可并行开发 |
| 账号模型设计欠考虑 | 全新建设无历史包袱，但模型一旦随业务端上线就难以调整 | 绑定关系按 1:N 预留、认证源可插拔；上线前做一次模型评审（对照二期目标校验） |
| 归并规则随业务变化 | 未来新增余额/积分等资产类业务后，合并规则需补充 | 新业务上线时将归并规则评审纳入上线检查清单（当前无此类冲突，按默认预案执行） |
| 认证中心单点故障 | 全站无法登录 | 故障时已登录用户凭本地 token 继续核心业务（只读），新登录拒绝并明确提示；上线前压测与故障演练 |
| 合规风险 | 无感知注册、注销流程不合规 | 上线前法务过审用户协议与注销流程 |
