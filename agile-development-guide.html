一、需求 vs Issue：两条录入通道

我们的工具里有两个入口，按事情的大小和来源区分：

入口 录什么 例子
需求池 新功能、复杂些的优化 接入微信支付、重构登录体系
全部 Issues 上线后发现的 bug、小优化 验证码无法刷新、按钮文案调整

判断标准一句话：

要规划、要排期、改动较大的 → 建需求；上线后冒出来的问题或小改动 → 直接建 Issue。

Issue 的三种类型

类型 编号前缀 用途 例子
工单 TKT 小优化、一般任务 登录页文案微调
缺陷 BUG 上线后发现的系统缺陷 登录时验证码无法刷新
备忘 — 待办提醒、临时记录 记得关注某接口报错率

新功能、复杂优化不要直接建成工单——先进需求池，经过规划后再拆解执行。

Issue 状态流转

工具里 Issue 的完整状态：

待办池 → 待处理 → 进行中 → 评审中 → 已完成
                                 → 已取消
状态 在我们流程里的含义
待办池 先记下来，还没确定要不要做 / 什么时候做
待处理 确定要做，等待认领或排期
进行中 有人正在处理
评审中 处理完成，等待验证 / Review
已完成 验证通过，闭环
已取消 确认不做了

使用约定：

  • 开工前从“待处理”认领，状态改为“进行中”
  • 完成后改“评审中”，由验证人确认后勾“已完成”
  • 卡住时保持当前状态，在描述或评论里写明阻塞点

需求状态流转

工具里需求的完整状态：

草稿 → 评审中 → 已批准 → 开发中 → 已交付
                              → 已拒绝
状态 在我们流程里的含义
草稿 产品经理还在梳理，未提交评审
评审中 已提交，等待团队评审
已批准 评审通过，等待排期开发
开发中 正在开发实施
已交付 上线且产品经理验收通过，方案落地
已拒绝 评审不通过或确认不做

使用约定：

  • 需求按功能性 / 非功能性分类
  • 产品经理负责推动状态前进，尤其是“开发中 → 已交付”，必须亲自验收后才改
  • Issue 可通过“关联需求”字段挂到需求下，方便追溯（如某需求上线后的 bug）

二、模板与示例

Issue 标题格式

统一用 [模块] 动作 + 对象：

❌ 坏标题 ✅ 好标题
YK测试 [登录] 修复验证码无法刷新
测试任务 [支付] 微信回调失败时增加重试
任务02 [首页] 调整按钮文案为“立即开通”

好标题的标准：不看描述也知道动的是哪个模块、要做什么。

Issue 描述模板 

【背景】问题/优化来自哪里（线上反馈、内部发现、用户投诉）
【现象 / 目标】现在什么样 → 期望什么样
【验收标准】
1. ……
2. ……
【其他】截图、日志、复现步骤、关联需求（FR-x）

小工单可以简化，但验收标准不能省。

写 Issue 的四条原则

  1. 标题清晰：按上面的格式命名。
  2. 可验收：描述里写清楚“做到什么程度算完成”。
  3. 粒度适中：太大的拆成多个工单，太小的合并。
  4. 及时更新状态：避免列表信息过期。

需求描述模板 

【背景】为什么做（用户/业务痛点，有什么数据或反馈支撑）
【目标】做到什么程度
【验收标准】
1. ……
2. ……
【范围】本期做什么 / 明确不做什么
【依赖】设计稿、接口、第三方配合事项

需求评审看什么

  • 背景和目标是否说清楚
  • 验收标准是否可验证
  • 技术可行性和大致工作量
  • 优先级是否合适

需求如何拆成 Issue

  • 需求（FR-x）批准后，拆成若干工单/任务执行。
  • 拆出的 Issue 通过「关联需求」字段挂到 FR-x 下，需求页的进度（如 0/3）自动反映完成情况。
  • 拆分粒度：单个 Issue 尽量 1～3 天能完成，超过就继续拆。
  • 拆解由产品经理和开发在评审通过后、开工前共同完成。

三、我们团队的轻量协作方式

我们不套用 Scrum 或 Kanban 的完整框架，而是围绕三个核心习惯运转：

核心习惯 1：任务可见

所有工作都录入工具的 全部 Issues 里，包括：

  • 谁在做什么（负责人）
  • 当前状态
  • 截止时间
  • 阻塞点

注意：工具里的“迭代 Sprint”和“产品待办”模块是否启用由开发团队决定——团队规模扩大或需要更强的节奏感时可以开启，开启前先评估是否增加流程负担。新功能、复杂优化放需求池，排期规划后执行；上线后的 bug、小优化直接建 Issue。

核心习惯 2：阻塞不隔夜

谁遇到阻塞，当天在群里@相关人说明：

  • 阻塞在哪里（贴上 Issue 编号，如 TKT-3）
  • 需要谁帮忙
  • 期望什么时候解决

核心习惯 3：定期对齐

站会不是每天开，而是每隔几天开一次同步实时会议（synchronous）。具体开法见第七章。

四、日常工作流程 

事情来了
  │
  ├── 新功能 / 复杂优化 ──→ 建到「需求池」，排期规划后拆解执行
  │
  └── 上线后的 bug / 小优化 ──→ 直接建 Issue
                                 （缺陷 BUG / 工单 TKT，填负责人 + 截止时间 + 验收标准）
  │
  ▼
每个人异步推进
有阻塞当天在群里说（附 Issue 编号）
  │
  ▼
每隔几天开一次同步会
对着「全部 Issues」的待处理列表过一遍
只处理阻塞和协作点
  │
  ▼
完成时勾到「已完成」
必要时简单同步结果

五、上线与验收：产品经理跟进到方案落地为止

开发完成 ≠ 需求完成。 一个需求只有真正上线、按预期运转，才算闭环。产品经理要从需求提出一路跟进到方案落地实施为止，不是提完需求就结束。

功能开发完成后的流程 

开发完成（需求状态：开发中）
  │
  ▼
提测（开发自测 → 测试验证）
  │
  ▼
上线发布
  │
  ▼
产品经理验收：功能是否按预期落地
  │
  ▼
上线后观察效果
  ├── 发现问题 / 小优化 ──→ 建 Issue（BUG / TKT，关联需求）
  └── 符合预期 ──→ 需求勾「已交付」，闭环

产品经理的跟进职责

  1. 需求阶段：在需求池里写清楚背景和验收标准。
  2. 开发阶段：跟进进度，及时解答需求疑问，参与同步会澄清目标。
  3. 测试/上线阶段：确认提测、上线的安排，协调相关方配合。
  4. 验收阶段：功能上线后亲自验证——方案是否按预期落地、交互和流程是否符合设计要求。
  5. 闭环阶段：上线后观察一段时间，发现 bug 或小优化及时建 Issue 跟进；确认稳定后需求才算真正完成。

一句话：产品经理对“方案有没有真正落地”负责，而不只是“需求有没有提”。

六、角色职责速查表

每个环节谁负责什么，一张表查清楚：

环节 产品经理 开发 测试 / 验证人
需求提出 建需求（草稿），写清背景、目标、验收标准 — —
需求评审 发起评审，讲清目标和优先级 评估技术可行性、工作量、风险 评估测试点、验收边界
需求开发 答疑、跟进进度 认领并开发，及时更新状态 提前准备测试点
提测上线 确认上线安排、协调相关方 自测通过后提测 测试验证，反馈问题
上线验收 亲自验收，确认后勾「已交付」 配合修复验收发现的问题 协助复验
Issue 创建 上线后问题 / 小优化建 Issue 发现问题也可直接建 Issue 测试中发现问题建 Issue
Issue 处理 跟进高优先级 Issue 的闭环 认领：待处理 → 进行中 → 评审中 验证通过后勾「已完成」
同步会 澄清目标、协调跨方阻塞 更新状态、暴露阻塞 同步验证进展
阻塞响应 被@后当天响应 被@后当天响应 被@后当天响应

使用约定：

  • 谁认领谁更新状态，状态长时间不动的 Issue 会在同步会上被过问到。
  • 「评审中 → 已完成」由验证人确认，不是开发自己勾完。
  • 需求的「开发中 → 已交付」由产品经理确认，参照第五章验收职责。
  • 不在表里的角色（如设计、运营）按需被@参与，无固定职责。

七、同步会 SOP 与异常场景

会议 SOP

项目 约定
频率 每隔几天一次（一周 2～3 次），固定时间
时长 不超过 30 分钟
主持人 固定一人或轮流，负责控场、记录结论
会前 各自更新 Issue 状态；进度复杂的在 Issue 评论里写清：已完成部分、剩余部分、当前阻塞
会中 对着「全部 Issues」的待处理/进行中列表过，只聊三件事：①谁卡住了、需要什么帮助 ②接下来 1～2 天哪些事需要协作 ③有没有人对目标理解不一致
会后 结论和分工写回相关 Issue 评论或群里，@到人

会议不做“昨天做了什么”的轮流汇报——状态在工具里，开会只看工具。

异常场景处理

场景 处理约定
线上紧急 bug 直接建 BUG 标高优先级，群里@负责人当天处理，不等同步会
需求做到一半范围变了 产品经理在需求评论里说明变化、更新验收标准，相关人确认后继续
待处理超一周没人动 同步会上过问：认领、降级回待办池、或取消
阻塞超一天未解决 升级给产品经理/负责人协调资源
时间凑不齐开不了会 改异步：各自在群里按三问更新（完成了什么/计划什么/有无阻塞），阻塞单独@人

八、时效约定（轻量 SLA）

事项 约定
线上 BUG 响应 当天响应，先确认影响和临时方案
一般 Issue 认领 「待处理」停留不超过一周
阻塞响应 被@后当天响应
需求评审 提交评审后 3 个工作日内给结论
上线验收 上线后 3 个工作日内产品经理完成验收

以上是建议值，团队可按实际情况在同步会上调整；调整后的版本更新到本章。

九、分布式团队的关键原则

  1. 异步优先

    • 能用 Issue 评论、文档说清楚的事，就不开实时会议。

  2. 必要的文档不能省

    • 需求说明、技术决策、新人上手文档、问题处理手册，都要写下来（可放在需求池或共享文档中）。

  3. 自动化是协作的基础

    • CI/CD、自动化测试要做好。分布式团队没法随时问“你本地能跑吗”，主干必须随时可构建。

  4. 保留同步窗口

    • 如果跨时区，每天保留一个有交集的时间段（如 2 小时），只处理必须讨论的事。

  5. 不要为了开会而开会

    • 同步会议成本高，只用来解决“文字说不清楚”的事。

十、一句话总结

对我们团队来说，敏捷不是 Scrum 或 Kanban，而是：任务看得见（全部 Issues）、阻塞不隔夜（当天@人）、偶尔对齐方向（同步会）、优先异步沟通。
